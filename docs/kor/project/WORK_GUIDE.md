## Sprint 02에서 확정한 내용

서울시 상권분석서비스의 점포·추정매출·길단위인구 데이터를 `상권코드 × 서비스업종코드 × 기준년분기`로 결합하는 방안을 채택했습니다. 실제 데이터로 다음 항목을 확인했습니다.

1. 점포·매출의 실제 컬럼, 자료형, 2024~2025 분기 범위와 행 수를 기록했습니다.
2. 매출 키가 점포 키와 100% 결합됨을 확인했습니다.
3. 2024Q4→2025Q1 상권코드 연속성을 확인했습니다.
4. 길단위인구 Q1 표본의 상권 결합률이 99.97%임을 확인했습니다.
5. 공개 폐업률이 100을 넘을 수 있어 확률 타깃으로 사용하지 않기로 했습니다.
6. 기본 타깃을 다음 분기 폐업 발생 여부로 확정했습니다.
7. 원천 파일은 저장소에 커밋하지 않고 출처·라이선스·한계만 기록했습니다.

다음 중 하나라도 충족하지 못하면 실제 모델 학습으로 넘어가지 않습니다.

- 타깃이 미래 분기의 폐업을 나타내지 못한다.
- 설명변수와 타깃을 같은 공간·업종·시간 단위로 결합할 수 없다.
- 2024년 코드 변경을 합리적으로 연결하거나 분석 기간을 분리할 수 없다.
- 이용조건상 분석 또는 제출용 예시 데이터 제공이 어렵다.

## COD-193 포털 레시피 작성 순서

데이터 게이트를 통과한 뒤 [레시피 초안](../recipe/COD-193_DATA_RECIPE_DRAFT.md)을 다음 순서로 확정합니다.

1. 레시피 유형을 데이터레시피 또는 AI 레시피 중 실제 분석 수준에 맞게 선택합니다.
2. 레시피명, 활용 목적, 데이터 유형, 표준산업분류와 키워드를 일관되게 맞춥니다.
3. “얻을 수 있는 것”에는 결과물과 의사결정 사용자를 씁니다.
4. “필요한 이유”에는 현재 한계와 데이터로 해결 가능한 범위를 씁니다.
5. 최소 데이터 요건, 예측값, 별도 시스템 필요 여부를 명시합니다.
6. 테이블 정의서·템플릿·예시 데이터셋을 재배포 가능한 형태로 준비합니다.
7. 분석 전체 과정을 최대 6 STEP으로 작성합니다.
8. 결과 이미지와 해석을 한 쌍으로 최대 5개 준비합니다.
9. 실제 검증 결과에 근거한 성과지표를 최대 3개 작성합니다.
10. 단기·장기 활용방안, 기대효과, 한계와 오용 방지책을 함께 씁니다.

## 분석과 검증 규칙

- 관측창은 기준 분기 `t`까지, 타깃은 미래 `t+1`로 분리합니다.
- 무작위 분할보다 시간 순서 분할을 우선합니다.
- 직전 폐업 발생 여부나 업종별 과거 평균 위험도 같은 단순 기준선을 반드시 둡니다.
- 전체 평균 성능만 제시하지 않고 업종·자치구·상권 규모별 표본 수와 성능을 함께 봅니다.
- 소표본 집단은 병합·제외·경고 중 하나의 처리 규칙을 사전에 정합니다.
- 예측점수는 지원 검토용 상대 신호로 설명하고 개별 사업자의 폐업 확정값으로 사용하지 않습니다.
- 임대료처럼 확보하지 못한 변수는 사용했다고 쓰지 않고 한계로 남깁니다.

## 포털 제출 절차

공식 신청서 가이드상 데이터레시피 제안 유형은 다음 순서입니다.

1. 포털에서 데이터레시피 또는 AI 레시피를 먼저 생성합니다.
2. 경진대회 신청 화면에서 참가유형을 `데이터레시피 제안`으로 선택합니다.
3. 과제명과 300자 이상 서술 항목을 작성합니다.
4. `조회` 버튼으로 사전에 생성한 레시피를 선택합니다.
5. 레시피를 수정했다면 신청 화면에서 다시 선택·반영합니다.
6. 임시저장본을 검토한 뒤 최종 제출합니다.
7. 제출 시각, 선택 레시피와 접수 상태를 캡처해 보관합니다.

워크플로 URL·JSON은 신청서 가이드에서 분석도구 활용 유형의 추가 제출물로 안내됩니다. 다만 참가신청 양식의 공통 유의사항에는 워크스튜디오 분석 문구가 있으므로, 이 프로젝트는 지원 분석을 워크스튜디오에서 재현하고 제출 시점의 포털 필수항목을 다시 확인합니다.
